# Модель данных PostgreSQL

Это проект модели для MVP, а не описание уже реализованной базы. [Исходник ER-диаграммы](diagrams/07-data-model.mmd) хранится рядом с остальными схемами.

Каждый прогон использует одну неизменяемую версию сценария и одну версию цен. Человек и робот работают с одинаковой моделью данных и командами. Денежные значения и итоговые метрики рассчитывает движок, а LLM получает готовые результаты для разбора.

## Сущности и ключи

| Сущность | Что означает одна строка | Ключи и основные правила |
| --- | --- | --- |
| `instrument` | Идентичность инструмента во внешнем источнике | PK `id`, UK `external_uid`. Это справочник идентификаторов. Размер лота, шаг цены и другие параметры для расчёта фиксируются в версии данных, чтобы позднее изменение справочника не меняло старый прогон. |
| `market_event` | Сохранённая версия одного рыночного события из конкретного источника | PK `id`, UK `content_hash`. Храним ссылку, время события, время публикации и `available_at`, когда сведения стали доступны в источнике. `asset_codes` имеет тип `text[]`: коды инструментов нормализуются при импорте и используются в `search_events` и `load_history`. Исправленный текст создаёт новую запись. RAG получает сохранённый текст, а не меняющуюся страницу по URL. |
| `dataset_version` | Зафиксированный набор цен и параметров инструментов | PK `id`, UK `content_hash`. `data_kind` равен `HISTORICAL` или `SYNTHETIC`. `source_manifest` содержит происхождение набора и параметры генерации, `instrument_snapshot` фиксирует расчётные параметры инструментов. Опубликованную версию не редактируем. |
| `price_point` | Цена одного инструмента на одном шаге набора | Составной PK `(dataset_version_id, step_no, instrument_id)`. FK на версию набора и инструмент. Цена положительная, номер шага неотрицательный. Это последовательность цен для движка, а не OHLC-свеча с неизвестным порядком цен внутри дня. |
| `scenario_version` | Зафиксированная версия учебного сценария | PK `id`, FK `dataset_version_id`, UK `content_hash`. `definition` содержит условия, доступные действия и расписание раскрытия событий. Новые настройки создают новую версию. |
| `scenario_event` | Связь версии сценария с сохранённым событием, которое использовалось при подготовке | Составной PK `(scenario_version_id, market_event_id)`, оба поля FK. Связь сохраняет происхождение контекста RAG. `reveal_step` задаёт шаг раскрытия участнику. `NULL` означает контекст только для подготовки и разбора. Не каждое найденное событие обязательно используется в сценарии. |
| `simulation_run` | Одна попытка человека или робота | PK `id`, FK `scenario_version_id`. `owner_id` определяет владельца, `controller_mode` равен `HUMAN` или `BOT`. Храним состояние, текущий шаг, `state_version` и остаток денег. `initial_portfolio_snapshot` фиксирует начальные деньги и позиции и после старта не меняется. `settings_snapshot` фиксирует комиссии, выбранную цель, seed при его использовании и настройки робота. `engine_version` фиксирует версию расчёта. |
| `portfolio_position` | Текущее состояние одного инструмента в одной попытке | Составной PK `(run_id, instrument_id)`, оба поля FK. Количество лотов неотрицательное. Это состояние для быстрого ответа API; каждое изменение также отражается в журнале. |
| `sim_order` | Одна принятая заявка в попытке | PK `id`, FK на попытку и инструмент. `side` задаёт покупку или продажу. В MVP типы `MARKET` и `STOP_MARKET`, только целые положительные лоты. Для стопа нужна положительная `stop_price`. `accepted_step` фиксирует шаг, на котором команда была принята. |
| `sim_fill` | Единственное исполнение заявки в упрощённой модели MVP | PK `id`, UK/FK `order_id`. Составной FK `(dataset_version_id, step_no, instrument_id)` указывает на конкретную цену исполнения. В MVP частичных исполнений нет. Комиссия неотрицательная, цена и количество положительные. |
| `run_event` | Одна запись журнала одной попытки | Составной PK `(run_id, seq_no)`, FK `run_id`. Номер записи задаёт строгий порядок. Здесь сохраняются команды, их результаты, исполнение, изменение денег и смена состояния попытки. У события `STEP_COMPLETED` в `payload` обязательно есть рассчитанная стоимость портфеля `equity` после этого шага. Детали остальных событий зависят от `event_type`. |
| `run_metrics` | Итоговый набор рассчитанных метрик одной завершённой попытки | PK/FK `run_id`. Храним стоимость портфеля, финансовый результат после расходов, комиссии, максимальную просадку и достижение выбранной цели. `calculation_version` позволяет понять, по каким правилам посчитан итог. |
| `ai_review` | Состояние и результат AI-разбора завершённой попытки | PK/FK `run_id`. Отдельный `status`: `PENDING`, `RUNNING`, `COMPLETED` или `FAILED`. `input_hash` фиксирует входные результаты, `model_id` выбранную модель, `prompt_version` версию инструкций помощника, `result` текст разбора и ссылки на рассчитанные показатели. Ошибка LLM не меняет статус и результаты симуляции. |
| `product_event` | Одно продуктовое событие для автоматических метрик | PK `id` типа UUID одновременно защищает от повторной записи события. Обязательны `owner_id`, тип события, источник `UI` или `BACKEND`, время и `payload`. `run_id` является nullable FK: событие может произойти до запуска симуляции. Этот поток отделён от финансового журнала `run_event`. |

`PK` обозначает первичный ключ, `FK` ссылку на другую сущность, `UK` ограничение уникальности. Составные FK и частичные уникальные индексы пояснены ниже, потому что Mermaid показывает их упрощённо.

## Воспроизводимость и доступ к данным

- После старта попытки нельзя заменить `scenario_version_id`. У неё уже зафиксирован `dataset_version_id`. Исторические и искусственные цены находятся в разных наборах с явной отметкой происхождения.
- Сценарий, версия цен, расчётные параметры инструментов, начальный портфель, настройки запуска и версия движка позволяют повторить прогон с теми же условиями. Полный replay дополнительно использует сохранённую последовательность команд из `run_event`.
- `current_step` определяет, что уже доступно участнику. API возвращает только открытые цены и события с `reveal_step <= current_step`. У робота нет прямого доступа к таблицам цен или будущим шагам. Для исторического сценария событие нельзя раскрывать раньше его `available_at`; для учебной временной шкалы раскрытие фиксируется отдельно в сценарии.
- Сохранённые события RAG служат контекстом при подготовке. Их наличие не означает, что сценарные цены предсказывают реальную реакцию рынка.

## Одна команда, одно изменение состояния

Каждая изменяющая команда API содержит `command_id`. Для записи `run_event` типа `COMMAND_RESULT` нужен частичный уникальный индекс `(run_id, command_id) WHERE event_type = 'COMMAND_RESULT'`. В такой записи обязательны `command_id`, `request_hash` и сохранённый ответ в `payload`. Другие записи журнала могут иметь тот же `command_id` для связи с командой.

Обработка команды блокирует строку `simulation_run` в транзакции. Если результат этого `command_id` уже есть и `request_hash` совпадает, API возвращает сохранённый ответ. При другом содержимом с тем же идентификатором возвращает конфликт. Для новой команды проверяются владелец, режим управления, состояние попытки и ожидаемый `state_version`. Устаревшая команда возвращает конфликт, чтобы участник сначала получил актуальное состояние. Затем движок меняет состояние, увеличивает `state_version`, сохраняет заявки, исполнения, позиции и журнал и фиксирует транзакцию. Это относится к заявкам, отменам и продвижению виртуального времени.

Так повторный запрос после потери ответа не создаёт вторую заявку, не списывает комиссию повторно и не переводит симуляцию ещё на один шаг. UK `sim_fill.order_id` дополнительно не допускает второго исполнения той же заявки в модели MVP.

## Расчёты и ограничения

Деньги, цены, стоимость портфеля, комиссии и доходность храним как `numeric` с согласованными масштабом и правилами округления. В Kotlin расчёт выполняется через `BigDecimal`. `float` и `double` не используются для денежных расчётов. Типы и масштаб полей уточняются в миграциях после выбора точности цен и валюты MVP.

В одной транзакции движок проверяет доступные деньги и количество лотов, рассчитывает исполнение и комиссию, меняет остатки и записывает событие. Для MVP без заёмных средств остаток денег и количество лотов не могут быть отрицательными. Инструмент исполнения должен совпадать с инструментом заявки, а версия набора цен должна совпадать с версией сценария этой попытки. Эти связи закрепляются составными FK там, где возможно, и проверкой движка внутри той же транзакции для связей через несколько таблиц.

В конце каждого шага движок рассчитывает `equity`: остаток денег плюс стоимость позиций по открытым ценам этого шага. Значение сохраняется в `run_event` типа `STEP_COMPLETED` вместе с номером шага. Для расчёта просадки используется весь этот временной ряд с начальной стоимостью портфеля, а не только начальное и конечное значения. Итоговый `max_drawdown_pct` считается кодом по падению от максимума, достигнутого к каждому шагу.

Завершение прогона атомарно: последние изменения состояния, финальная запись журнала, `run_metrics` и статус `FINISHED` фиксируются в одной транзакции. Продуктовое событие завершения от backend сохраняется в той же транзакции. Не должно возникать состояния `FINISHED` без итоговых метрик. Завершённая попытка больше не принимает торговые команды.

Итоговые метрики не изменяются ответом LLM. AI-разбор ссылается на конкретную попытку, её события и метрики; текст объяснения не является источником финансовых значений. Разбор можно повторить после ошибки LLM без повторного исполнения симуляции. Его статус хранится отдельно в `ai_review`.

## Автоматические продуктовые метрики

`product_event` позволяет считать, сколько людей собрали портфель, завершили симуляцию, открыли разбор, изменили портфель и повторили проверку. По `owner_id` связываются действия пользователя, по `run_id` попытка и её рассчитанные результаты. События с `run_id = NULL` сохраняют шаги до запуска прогона.

Повторная доставка того же события с тем же UUID не создаёт новую строку и не увеличивает счётчик. Backend определяет владельца из контекста запроса и проверяет допустимый тип события. Клиентские события описывают действия интерфейса, например открытие разбора. Они не подтверждают завершение расчёта, положительный финансовый эффект или запуск стратегии в Т-Инвестициях. Достижение цели определяется по `run_metrics`, а завершение прогона подтверждает backend.

Стоимость портфеля, доходность, комиссии и просадка не рассчитываются по клиентским событиям. Их источником остаются движок, `run_event` и `run_metrics`.

`owner_id` здесь является границей доступа API. Схема не задаёт отдельный сервис пользователей или готовую систему авторизации; способ идентификации владельца уточняется при реализации.

## Индексы для MVP

- B-tree на FK: `scenario_version.dataset_version_id`, `scenario_event.market_event_id`, `simulation_run.scenario_version_id`, `sim_order.run_id`, `sim_order.instrument_id`.
- Первичные ключи уже покрывают чтение цен по набору и шагу, позиций по попытке и журнала по попытке и порядку записей. UK `sim_fill.order_id` покрывает поиск исполнения заявки.
- Для RAG: GIN по `to_tsvector('russian', title || ' ' || body)` и по `asset_codes` в `market_event`, B-tree по `published_at` и `available_at`. Поиск по датам, инструментам и тексту использует сохранённые события PostgreSQL. Отдельная векторная база для MVP не выбрана.
- Для продуктовых метрик: B-tree `(owner_id, occurred_at)` и `(event_type, occurred_at)` в `product_event`, индекс по nullable FK `run_id`. PK `id` обеспечивает дедупликацию повторной доставки.

Это минимальная логическая модель. Таблицы авторизации, хранение LLM-диалогов, сложная бухгалтерская проводка и брокерские операции с реальными деньгами в неё не входят.
