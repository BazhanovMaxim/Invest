# Архитектурные решения MVP

Статус: проект для обсуждения разработки. Диаграммы описывают предлагаемые контракты и поведение, а не уже работающий сервис.

## Границы системы

Angular UI и торговый робот работают с одним HTTP API. У каждого прогона один владелец и один режим управления: человек или робот. Backend проверяет доступ к прогону. Исполнение произвольного кода робота на сервере в MVP не предусмотрено: робот является внешним API-клиентом.

T-Invest MCP в этом проекте является внешним источником рыночных данных. Его торговые методы не перенаправляются автоматически в наш движок. Если нужно проверить существующего MCP-робота без изменения его инструментов, потребуется наш отдельный MCP-адаптер поверх того же Run Service. Такой адаптер не включён в текущий MVP. Эта граница уточняет ранее добавленную бизнес-схему, где робот показан через MCP.

Развёртываем одно приложение Kotlin/Spring Boot и PostgreSQL. AI-Agent, RAG, симулятор и отчёты являются внутренними модулями backend. Отдельные микросервисы, брокер сообщений, Redis, S3 и векторную базу в этот вариант не закладываем: для согласованного MVP они пока не нужны.

## Ответственность модулей

| Модуль | За что отвечает |
| --- | --- |
| HTTP API | Доступ к прогону, валидация запросов, общий контракт UI и робота |
| Scenario Service | Сохранение и чтение неизменяемых версий сценария |
| AI-Agent | Планирование проверки, ограниченный цикл LLM и инструментов, итоговый разбор |
| LLM Gateway | Формат сообщений, вызовы модели, тайм-ауты, версия модели и промпта |
| RAG / Event Retrieval | Поиск событий и связанной истории с источниками, датами и версиями |
| Run Service | Состояние прогона, виртуальное время, идемпотентность и транзакции |
| Simulation Engine | Детерминированный расчёт исполнения, денег, позиций, комиссий и просадки |
| Result Service | Готовые численные результаты, журнал, сравнение попыток и сохранение AI-разбора |
| Data Import | Чтение внешних данных, нормализация и создание версионированных наборов |

В component-диаграмме стрелки обозначают вызовы и зависимости модулей. API запускает агента, а агент вызывает Scenario/Result Service через интерфейсы инструментов. Сохранение сценария и чтение результата не запускают агента повторно. Данные возвращаются вызвавшему модулю; обратные стрелки ответа здесь опущены.

## AI-Agent, LLM и RAG

До запуска агент получает цель, портфель, опыт и доступные пользователю действия. LLM запрашивает инструменты, backend выполняет разрешённый вызов и возвращает `tool_result` в модель. Агент ограничивает число шагов и общее время подготовки.

| Инструмент | Назначение | Когда доступен |
| --- | --- | --- |
| `search_events` | События по теме, активам, датам; ссылка и время публикации | Подготовка |
| `load_history` | Цены и параметры из конкретной версии данных | Подготовка |
| `save_scenario` | Сохранить ScenarioSpec и готовый учебный ценовой путь | Подготовка |
| `get_run_result` | Получить уже рассчитанные кодом метрики | После FINISHED |
| `get_run_journal` | Получить действия, исполнения и комиссии с идентификаторами | После FINISHED |

RAG в MVP использует фильтры и полнотекстовый поиск PostgreSQL. В контекст LLM попадают сами события и связанная история, а также источники и даты. Качество такой выдачи ещё предстоит проверить на выбранных событиях; переход к embeddings является отдельным решением, если простой поиск окажется недостаточным.

LLM может сформировать учебные события и параметры искусственного сценария, например падение и восстановление цены. Сохраняем готовую траекторию и версию правил до старта. Повторный запрос к модели не нужен для воспроизведения. Исторические данные и искусственные цены имеют разные версии и признаки происхождения. Учебный сценарий не является прогнозом реакции реального рынка.

Во время прогона наш агент не даёт подсказок и не выполняет команды. После финиша он получает готовые числа и журнал, объясняет результат со ссылками на действия и предлагает следующее изменение. Недоступность LLM не отменяет завершённую симуляцию: численный отчёт остаётся доступен.

## Детерминированное исполнение

MVP: две акции и денежный остаток, рыночные и упрощённые стоп-маркет заявки, без кредитного плеча. Это учебная модель исполнения, а не точная копия биржи. Частичные исполнения и модель стакана в этот вариант не входят.

1. Клиент видит Observation шага `n`.
2. Отправляет одно Decision с нулём или несколькими действиями. Пустой список означает «ничего не менять». Цены исполнения клиент не передаёт.
3. Backend проверяет владельца, статус и версию состояния, затем добавляет действия и переходит к следующему ценовому шагу.
4. Новые заявки могут исполняться начиная с `n+1`. Стоп проверяется по очередной заданной цене и исполняется по правилам сценария, включая возможный ценовой разрыв.
5. Движок возвращает изменения. Run Service сохраняет состояние, исполнения, журнал и ответ на команду одной транзакцией.

Каждая версия правил фиксирует комиссию, округление, порядок обработки заявок и поведение при нехватке денег или бумаг. Денежные значения хранятся в PostgreSQL `numeric` и рассчитываются через Kotlin/Java `BigDecimal`. Одной дневной свечи недостаточно для восстановления внутридневного порядка: учебный сценарий использует сохранённую последовательность ценовых шагов.

Только backend двигает виртуальные часы. В Observation попадают цены и события, доступные на текущем шаге. Будущая траектория и ещё не раскрытые события доступны движку, но не возвращаются человеку или роботу.

## Согласованность и ошибки

На одно Decision приходится одна транзакция PostgreSQL с блокировкой строки конкретного run. Повтор с тем же `commandId` и тем же содержимым возвращает сохранённый ответ без второго исполнения. Идентификатор с другим содержимым отклоняется. Устаревшие `expectedStep` или `expectedVersion` дают конфликт состояния, после которого клиент перечитывает Observation.

Внешних вызовов LLM, MCP и новостей внутри транзакции исполнения нет. Данные загружаются и фиксируются заранее. При откате транзакции шаг не считается принятым. Если ответ потерялся после COMMIT, клиент повторяет тот же `commandId`.

Run проходит состояния `CREATED -> RUNNING -> FINISHED`; техническая ошибка, после которой продолжение невозможно, переводит его в `FAILED`. AI-разбор имеет отдельный статус и не меняет статус успешно завершённого run.

## Автоматические метрики

Фиксируем создание портфеля, завершение прогона, открытие разбора, изменение стратегии и новую попытку. UI отправляет продуктовые события через общий API, backend сохраняет их в отдельный product_event. Завершение и численные улучшения фиксирует backend по рассчитанным данным. Считаем долю прошедших эти шаги, количество попыток до выбранной цели и возвраты пользователей. Улучшение результата считаем по заранее выбранной цели, например меньшей просадке или результату после расходов, при одинаковых сценарии, стартовых деньгах и правилах исполнения.

Подтверждённый переход к работе в Т-Инвестициях является будущей интеграцией, если банк предоставит такие события. Клик по ссылке не считаем запуском стратегии.
